User Guide

PRM-as-a-Judge v1.5

A practical toolkit for robot process auditing. Give it rollout videos and task descriptions; it produces normalized progress curves, case-level diagnostics, task summaries, and leaderboard-ready reports.

In the simplest workflow, the input is a JSONL manifest: each line describes one evaluation case and includes at least a unique case_id, a task description in task, and a video path in video. Specify the file and run one command to obtain evaluation results. You can also adjust sampling, evaluation modes, video views, GPU selection and multi-GPU execution, smoothing, metrics, and Process Reward Model (PRM) backends to suit your data format, evaluation goals, and compute resources.

用户指南

PRM-as-a-Judge v1.5

一个用于机器人过程审计的实用工具包。提供执行视频和任务描述后， 它会生成归一化进度曲线、单案例诊断、任务汇总，以及可用于排行榜的报告。

在最简用法中，输入为一个 JSONL manifest：每行描述一个待评估案例， 并至少包含唯一标识 case_id、任务描述 task 和视频路径 video。 指定该文件并运行一条命令，即可获得评估结果。你也可以根据数据形式、评测目标和计算资源， 调整采样、评估模式、视频视角、GPU 编号与多 GPU 并行、平滑方法、指标，以及 过程奖励模型（Process Reward Model，PRM）后端。

Overview

PRM-as-a-Judge evaluates the process of a robot rollout, not only the terminal outcome. A PRM backend estimates progress over time, then the metric stack turns that curve into interpretable signals about near success, stagnation, drawdown, recovery, and success quality. 

JSONL manifest -> PRM adapter -> normalized progress curve -> postprocess -> metrics/report
The default settings provide a fast and simple path to evaluation results. You can adjust the later stages according to your task, data format, runtime resources, and analysis goals.

Input

Each JSONL line is one rollout case with video paths, task text, optional labels, and metadata.

Judge

Adapters support pair-style PRMs such as Robo-Dopamine and sequence-style PRMs such as RoboMeter.

Report

Outputs include raw and processed curves, per-case metrics, task summaries, leaderboards, and plots.

Quick Start

The dependency-free base toolkit supports Python 3.10 or newer. The released Robo-Dopamine constraints were validated on Linux x86_64, Python 3.10, and CUDA 12.8, so the following reproducible setup uses Python 3.10.

1. Clone the repository

git clone https://github.com/Yuheng2000/PRM-as-a-Judge.git
cd PRM-as-a-Judge

2. Create and activate a Conda environment

conda create -n prm-judge python=3.10 -y
conda activate prm-judge

3. Install the default backend dependencies

The default runner uses Robo-Dopamine, so install the toolkit with the dopamine dependency group and the verified complete constraints file. 

python -m pip install --upgrade pip
python -m pip install -e ".[dopamine]" \
  -c constraints/dopamine-cu128-py310.txt
python -m pip check

4. Download the public Preview checkpoint

The public default is Robo-Dopamine-GRM-2.0-8B-Preview. Pin the validated revision when downloading it into the default directory; see the official hf download guide for authentication and cache options: 

hf download tanhuajie2001/Robo-Dopamine-GRM-2.0-8B-Preview \
  --revision 980f3d1819c870f62c36169a9486e971049bb09a \
  --local-dir PRM/Robo-Dopamine-GRM-2.0-8B-Preview

A compatible Pro checkpoint is still supported but is not the public default. Use it only by explicitly setting PRM_PATH=/path/to/Robo-Dopamine-GRM-8B-Pro.

5. Create a manifest

Put your rollout paths and task descriptions in a JSONL file. Videos can stay anywhere on disk; paths may be absolute or relative to the manifest. 

{"case_id":"case_001","task_name":"put_can","task":"put the can into the basket","video":"videos/case_001.mp4","model":"pi0"}

6. Run the default evaluation

The default runner uses Robo-Dopamine in incremental mode, the default sampling interval, GPU 0, outlier replacement, and weighted smoothing. 

MANIFEST=/path/to/cases.jsonl bash eval/run_eval.sh

7. Add visualizations

MANIFEST=/path/to/cases.jsonl \
VISUALIZE=1 \
bash eval/run_eval.sh

Run the dependency-free recorded smoke test

The bundled manifest contains two synthetic progress curves and points to real bundled MP4 files, so it validates metrics, CSV, Markdown, HTML, and video paths without loading a model. 

python -m pip install -e .
prm-judge eval \
  --manifest eval/examples/manifest_recorded.jsonl \
  --prm recorded \
  --visualize
After writing all available per-case, summary, and visualization artifacts, the CLI exits 1 if any case has status=error. Pass --allow-partial only when your automation intentionally accepts error records; it keeps them and exits 0. Successful runs and valid dry-runs exit 0.

Run with RoboMeter

RoboMeter is a sequence-style backend. The runner can start a local RoboMeter HTTP server, wait for /health, evaluate cases, and shut the server down after the run. 

PRM=robometer \
MANIFEST=/path/to/cases.jsonl \
bash eval/run_eval.sh

Reuse an already running server when you want to manage the model process yourself:

PRM=robometer \
MANIFEST=/path/to/cases.jsonl \
ROBOMETER_SERVER_URL=http://localhost:8000 \
ROBOMETER_AUTO_START=0 \
bash eval/run_eval.sh
When PRM=robometer, eval/run_eval.sh uses ROBOMETER_PYTHON for both the runner and the auto-started server so video dependencies such as decord or opencv-python are available. If you call prm-judge directly, run it from an environment that can decode your videos.

Manifest Format

The recommended default input is a manifest file. It uses UTF-8 JSONL, with each line describing one rollout case. Paths may be absolute or relative to the manifest file.

Single View

{"case_id":"case_001","task_name":"put_can","task":"put the can into the basket","video":"videos/case_001.mp4"}

Main View with a Single-Arm Robot Wrist View

{"case_id":"case_002","task_name":"put_can","task":"put the can into the basket","video":"high.mp4","wrist_video":"wrist.mp4"}

Main View with Bimanual Robot Wrist Views

{"case_id":"case_003","task_name":"put_can","task":"put the can into the basket","video":"high.mp4","left_wrist_video":"left.mp4","right_wrist_video":"right.mp4"}

With Goal Image and Benchmark Label

{"case_id":"case_004","task_name":"arrange_flowers","task":"arrange the flowers in the vase","video":"h.mp4","wrist_video":"w.mp4","goal_image":"goal.png","label":"success","benchmark":"RoboTwin","model":"pi0"}

With Precomputed Progress

{"case_id":"case_005","task_name":"open_drawer","task":"open the drawer","video":"drawer.mp4","progress_path":"curves/case_005.json"}
Field Requirement Description
case_id ● Required Stable case identifier. The loader raises an error if it is missing.
task ● Required Natural-language task description passed to the PRM backend. instruction and task_prompt are accepted aliases.
video ● Required Main rollout video path, normally a third-person or overhead view. If no wrist fields are provided, the Dopamine adapter reuses it for all camera slots.
wrist_video ○ Optional The wrist-camera path of a single-arm robot. Dopamine duplicates it into the two wrist input slots required by the backend. Do not combine it with the bimanual wrist fields.
left_wrist_video / right_wrist_video ○ Optional pair Left and right wrist-camera paths for a bimanual robot. The two fields must be provided together and cannot be combined with wrist_video.
videos Legacy compatibility only Older objects using aliases such as high, left, and right remain readable, but new manifests should use the four top-level video fields.
task_name ○ Optional Short grouping key used for filtering, output paths, summaries, and leaderboard rows. Falls back to task.
goal_image ○ Optional Image of the desired final state. Useful when the task text is ambiguous or the target layout matters.
label ○ Optional success or failure. The label-based grouping also accepts common boolean aliases such as true, false, 1, and 0. Use --success-source label when benchmark labels should define grouping.
benchmark ○ Optional Dataset or benchmark name copied into reports.
model ○ Optional Policy, robot model, or method name used for leaderboard aggregation.
metadata ○ Optional Free-form JSON object copied into outputs for reproducibility.
progress / progress_path ○ Optional Precomputed progress curve for --prm recorded, debugging, or external PRM integration.

Outputs

Outputs are written to eval/results/run_YYMMDD_HHMMSS/ by default.

File Use it for
run_params.json Resolved CLI options and runtime settings for reproducibility.
run_summary.json Total, successful, failed, and aggregated metric counts for the run.
per_case.jsonl Raw and processed progress curves plus metrics for each rollout.
benchmark/model/task/case/result_summary.json Per-case result file under the case output directory.
summary.csv Task-level v1.5 metrics and success/failure grouping.
leaderboard.csv Model-level summary for comparing policies.
report.md Human-readable run report for sharing results.
discovery_manifest.json Resolved input paths, runtime choices, and reproducibility metadata.
robometer_server_PORT.log RoboMeter server log when auto-start is used.
visualizations/curve_metrics.csv Per-case curve metrics when --visualize or VISUALIZE=1 is enabled.
visualizations/report.html Local interactive HTML report generated when --visualize or VISUALIZE=1 is enabled. Open it in a browser to review rollout videos, progress curves, live frame metrics, milestones, and sortable model-level, model-by-task, and per-case metric tables.
visualizations/visualization_report.md Visualization artifact index and plot-generation status.
visualizations/case_plots.csv Index of generated per-case figures.
visualizations/cases/*.png Raw and processed progress curve plots when matplotlib is installed.

ECharts 5.5.1 is bundled and embedded into every generated HTML report, so charts work without internet access. Videos stay as external assets and use the paths recorded in the run. Direct file opening remains compatible while those paths are accessible, but copying only report.html does not copy videos. Missing or moved videos show a media error even though the offline charts continue to render.

Generate visualizations after a run has finished:

prm-judge visualize --run-root eval/results/run_YYMMDD_HHMMSS

For reliable MP4 playback and seeking, use the built-in Range-aware server:

prm-judge serve \
  --run-root eval/results/run_YYMMDD_HHMMSS \
  --host 127.0.0.1 \
  --port 8000

Open http://127.0.0.1:8000/report.html. For a remote server, keep the report service on loopback and create a tunnel from your workstation:

ssh -L 8000:127.0.0.1:8000 user@server
Do not use python -m http.server for these MP4 reports: it does not reliably provide the byte-range behavior required for seeking. The built-in server exposes only videos recorded by the selected run through opaque media tokens.

Default Settings

Defaults are selected to make the first run easy and reproducible. Treat this as the baseline configuration before tuning for speed, sampling density, or a different PRM backend.

Setting Default Change when
PRM backend dopamine You want a sequence-style backend such as robometer, or a custom adapter.
Dopamine checkpoint PRM/Robo-Dopamine-GRM-2.0-8B-Preview You explicitly pass another compatible checkpoint with PRM_PATH.
Dopamine mode incremental You want goal-relative scoring with backward, or start-relative scoring with forward.
Frame interval 72 You need denser curves for short or fast tasks, or faster inference for long videos.
Batch size 10 You are memory-limited or want higher throughput on larger GPUs.
GPU selection GPUS=0 You have multiple local GPUs and want to shard cases across them.
Outlier removal Local median replacement Your PRM is already stable or you are auditing raw model behavior.
Smoothing [0.1, 0.2, 0.4, 0.2, 0.1] You need a narrower or wider temporal window for very noisy or very fast progress.
Case-error exit status Exit 1 after writing artifacts Your automation intentionally accepts partial results and passes --allow-partial.

Choose a PRM Backend

The toolkit can evaluate rollouts with different PRM backends. The default Dopamine backend is ready for a first run, and you can switch to RoboMeter, recorded curves, or your own PRM when your task needs a different progress estimator. After a backend produces a progress curve, the postprocessing and metric pipeline are shared.

Use case Recommended backend Why
First run or ordinary batch evaluation dopamine with EVAL_MODE=incremental Stable default, simple one-command path, and supports main-only, single-arm, and bimanual video layouts.
Repeated or context-dependent motion robometer Sequence-style judging can use longer temporal context than local pair comparison.
Debugging metrics without loading a model recorded Uses progress or progress_path from the manifest.
Your own PRM or reward model Custom adapter Return absolute progress in [0, 1], or configure normalization before metrics. See Custom PRM for the adapter steps.

Dopamine Modes

Robo-Dopamine is a pair-style PRM. It constructs a progress curve by scoring sampled states with one of three comparison modes.

Mode What is compared How progress is interpreted When to use
incremental (default) Previous sampled state as before, current sampled state as after. The model score is treated as a local progress change and accumulated over time. Default v1.5 mode for local step-wise change analysis. Consider a larger FRAME_INTERVAL if adjacent samples are too similar.
forward Start frame as before, current sampled state as after. The model score is treated as the current absolute progress estimate. Use it when start-to-current change is easier to judge than distance to the goal image.
backward Goal image as before, current sampled state as after. The model score is converted to progress with progress = 1 + score. Use it when a goal image or goal placeholder is available and goal-relative scoring is preferred.

Examples:

EVAL_MODE=incremental MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh
EVAL_MODE=forward MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh
EVAL_MODE=backward MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh
Pair-style judging can struggle with repeated or context-dependent motions because a local pair may not reveal whether the policy is making progress or simply moving back and forth. For these cases, compare results with a sequence-style backend such as RoboMeter.

Views and Goal Images

Multi-view and goal-image inputs are optional, but they often improve judgment quality for manipulation tasks where progress is hidden from a single camera.

Canonical video fields

  • video: required main, third-person, or overhead view. This is the default view for RoboMeter.
  • wrist_video: the only wrist camera of a single-arm robot. Dopamine duplicates it into the backend's two wrist input slots.
  • left_wrist_video and right_wrist_video: the left and right wrist cameras of a bimanual robot; provide both fields together.

Use wrist_video for a single-arm robot or the left/right wrist pair for a bimanual robot, not both. For Robo-Dopamine, the adapter expands video into the main camera slot, reuses wrist_video for both wrist slots, or maps the bimanual left/right wrist fields one-to-one. If only video is provided, the adapter reuses it for all camera slots so quick tests still work. Older videos objects with high, left, and right remain readable for compatibility.

For RoboMeter, the current HTTP adapter evaluates one selected view from the manifest and uses video by default. Set ROBOMETER_VIEW to wrist_video, left_wrist_video, or right_wrist_video to choose another view. For a single-arm case, its wrist_video can satisfy either left- or right-wrist selection required by the adapter. Old aliases such as high, left, and right are still accepted. Other missing non-default views raise an error instead of silently using another camera. 

PRM=robometer ROBOMETER_VIEW=left_wrist_video MANIFEST=cases.jsonl bash eval/run_eval.sh

When to add a goal image

  • Use goal_image when the desired final arrangement is specific, such as object layout, color order, or target container.
  • Omit it for simple semantic tasks where the language instruction is enough.
  • If omitted, the runner can fall back to eval/examples/blank.png when the backend requires an image field.

Multi-GPU

The default uses one GPU to keep the command predictable. On larger batches, set GPUS or pass --gpus to shard cases across local devices. 

GPUS=0,1,2,3 MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh

Each worker loads one PRM instance on its assigned GPU, processes its shard, and the runner merges shard outputs at the end. This is simple local data parallelism and is usually enough for evaluation batches.

You can also ask the runner to choose GPUs automatically. In the current implementation, GPUS=auto queries nvidia-smi, selects devices whose used memory is below 1024 MiB, and falls back to GPU 0 if no such device is found. 

GPUS=auto MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh

For RoboMeter multi-GPU runs, each shard uses ROBOMETER_SERVER_PORT + shard_index for an auto-started server, so choose a free base port when running several evaluations on the same machine.

Progress Standard

The metric stack consumes normalized absolute progress curves. Every PRM adapter should eventually produce: 

progress[t] in [0, 1]
PRM output Convert before metrics
Absolute progress in [0, 1] Use directly, then clip small numerical overflow.
Absolute progress in [0, 100] Divide by 100 with --normalize 0_100.
Step-wise delta progress Use --source-type delta, accumulate over time, then clip to [0, 1].
Uncalibrated reward or similarity Add adapter-specific calibration before metric computation.

Do not force the curve to be monotonic. Regressions and oscillations are meaningful signals used by drawdown, recovery, stagnation, and regret metrics. Results should store both progress_raw and progress_processed.

Postprocessing

The default pipeline is modular:

  1. Normalize the PRM output to absolute progress in [0, 1].
  2. Clip values to [0, 1].
  3. Replace isolated local outliers with the local median. The default threshold is 0.35.
  4. Smooth with a weighted temporal window.
p'_t = 0.1*p_{t-2} + 0.2*p_{t-1} + 0.4*p_t + 0.2*p_{t+1} + 0.1*p_{t+2}

This default is meant to reduce isolated spikes and saw-tooth artifacts without hiding real regressions. It is especially useful when a human can see a clear upward trend but local pair judgments alternate between progress and no progress.

Disable postprocessing when you are debugging raw PRM behavior:

prm-judge eval --manifest cases.jsonl --outlier-method none --smoothing none

Change the smoothing weights from the CLI:

prm-judge eval --manifest cases.jsonl --smoothing-weights 0.05,0.15,0.6,0.15,0.05

The weight list should have odd length, non-negative values, and a positive sum. It is normalized automatically. For deeper customization, edit eval/prm_judge/curves.py, especially parse_smoothing_weights, weighted_smooth, and PostprocessConfig.smoothing_weights.

Metrics

Metrics are computed from the processed progress curve unless otherwise noted. Use raw curves for debugging and processed curves for the default evaluation report.

Case-Level Metrics

Metric Interpretation
MaxP Maximum progress reached. Useful for failed rollouts that still got close to success.
M25, M50, M75 Milestone indicators showing whether the rollout crossed progress thresholds.
SR Success indicator at the success threshold, default 0.99.
PPL Progress-weighted path length anchored at the best reached progress.
CRA Cumulative regret after regressions. Compare it under similar success or progress conditions.
Stag Fraction of near-stagnant transitions. Read it together with video length and data collection style.
MDD Maximum progress drawdown.
Rec Recovered progress after the deepest drawdown trough.
DRR Robustness score, approximately (Rec + epsilon) / (MDD + epsilon), clipped to 1.

Group-Level v1.5 Metrics

Metric Applies to What it tells you Formula used by default
MaxP-F Failed trajectories How far failed rollouts got before failing. Mean MaxP over trajectories with SR_trace = 0.
FNS Failed trajectories Near-success quality of failed rollouts, combining best reached progress and milestone crossings. 0.5 * MaxP + 0.3 * M75 + 0.2 * M50; successful trajectories contribute 0.
SQS Successful trajectories Execution quality among successes, rewarding efficient, low-regret, low-stagnation curves. 0.5 * PPL + 0.3 * (1 - CRA) + 0.2 * (1 - Stag); failed trajectories contribute 0.
RBS All trajectories Robustness after the largest drawdown. Mean trajectory min(1, (Rec + epsilon) / (MDD + epsilon)).
OAS All trajectories Overall auditing score combining success, failed-case progress, recovery, and success quality. 0.3 * SQS_trace + 0.2 * FNS_trace + 0.2 * RBS_trace + 0.3 * SR_trace, averaged over trajectories.
Some diagnostics are conditional. For example, CRA is most informative when comparing rollouts that both achieved similar progress. A completely stagnant curve may have low regret but still be a poor rollout. By default, success grouping uses MaxP >= --success-threshold. Use --success-source label only when benchmark labels should define success and failure.

Custom PRM

The toolkit separates two responsibilities: a PRM adapter produces a progress curve, and the metric stack computes diagnostics from the standardized curve. This makes it possible to use PRMs beyond Dopamine.

Minimal integration steps

  1. Create a new adapter file under eval/prm_judge/prm/ and subclass BasePRMAdapter.
  2. Implement predict(case, output_dir) so it reads the manifest case, runs your PRM, and returns a ProgressTrace.
  3. Register the backend name in eval/prm_judge/cli.py: add it to the --prm choices and create the adapter in build_adapter.
  4. Make sure the returned progress is absolute [0, 1], or run with the matching --normalize and --source-type options.
  5. Evaluate with prm-judge eval --prm your_backend --manifest cases.jsonl.

Adapter checklist

  • Read EvalCase fields such as videos, task text, goal image, and metadata.
  • Run your PRM and return a progress sequence aligned to sampled frames or video time.
  • Decide whether the output is absolute progress, step-wise deltas, or another score.
  • Decide whether the scale is [0, 1], [0, 100], or uncalibrated.
  • Prefer returning absolute progress in [0, 1]. If not, pass the matching --normalize and --source-type options for the whole run.
from prm_judge.prm.base import BasePRMAdapter
from prm_judge.schema import EvalCase, ProgressTrace

class MyAdapter(BasePRMAdapter):
    def predict(self, case: EvalCase, output_dir):
        scores = run_my_model(case.videos, case.task, case.goal_image)
        return ProgressTrace(
            case_id=case.case_id,
            progress=scores,
            source_scale="0_1",
            source_type="absolute",
        )

Existing adapters under eval/prm_judge/prm/ can be used as templates. recorded.py is the smallest example, while robometer.py shows how to wrap an external model service. Document the model's output scale, semantics, required views, goal-image behavior, and runtime requirements next to your adapter.

RoboMeter as an example

RoboMeter is integrated as a sequence-style backend through an HTTP adapter. It reads outputs_progress.progress_pred as an absolute progress curve in [0, 1]. Because it reasons over a longer sequence, it is a useful comparison point for repeated-motion cases where local pairwise judging is not enough.

When you reuse an existing RoboMeter server, PRM-as-a-Judge checks /model_info and requires the server model path to match PRM_PATH. This helps avoid accidentally evaluating with an old checkpoint. The adapter uploads frame arrays as .npy multipart files, which keeps long-video requests manageable.

概览

PRM-as-a-Judge 评估的是机器人执行过程，而不只是最终结果。 PRM 后端会估计随时间变化的进度，随后指标栈将这条曲线转换为关于 接近成功、停滞、回撤、恢复和成功质量的可解释信号。 

JSONL manifest -> PRM adapter -> normalized progress curve -> postprocess -> metrics/report
默认设置提供了一条快速、简单的评估路径。你可以根据任务、数据格式、运行资源和分析目标， 调整后续阶段的配置。

输入

JSONL 的每一行表示一个执行案例，包含视频路径、任务文本、可选标签和元数据。

评判

适配器支持 Robo-Dopamine 这类成对比较式 PRMs，也支持 RoboMeter 这类序列式 PRMs。

报告

输出包括原始曲线和处理后曲线、单案例指标、任务汇总、排行榜和图表。

使用 RoboMeter 运行

RoboMeter 是序列式后端。运行器可以启动本地 RoboMeter HTTP 服务器， 等待 /health，评估案例，并在运行结束后关闭服务器。 

PRM=robometer \
MANIFEST=/path/to/cases.jsonl \
bash eval/run_eval.sh

当你希望自行管理模型进程时，可以复用已经运行的服务器：

PRM=robometer \
MANIFEST=/path/to/cases.jsonl \
ROBOMETER_SERVER_URL=http://localhost:8000 \
ROBOMETER_AUTO_START=0 \

当 PRM=robometer 时，eval/run_eval.sh 会同时为运行器 和自动启动的服务器使用 ROBOMETER_PYTHON，确保可用 decord 或 opencv-python 等视频依赖。如果直接调用 prm-judge，请在能够解码你的视频的环境中运行。

默认设置

默认设置的选择目标是让首次运行简单且可复现。在为速度、采样密度或不同 PRM 后端 调优之前，可以把它作为基线配置。

设置 默认值 适用调整场景
PRM 后端 dopamine 当你需要 robometer 这样的序列式后端，或自定义适配器时。
Dopamine checkpoint PRM/Robo-Dopamine-GRM-2.0-8B-Preview 显式通过 PRM_PATH 传入其他兼容 checkpoint 时。

批大小 10 当显存受限，或希望在更大 GPUs 上获得更高吞吐时。
GPU 选择 GPUS=0 当你有多个本地 GPUs，并希望把案例分片到不同设备时。

选择 PRM 后端

该工具包可以使用不同 PRM 后端评估执行过程。默认 Dopamine 后端已经适合首次运行； 当任务需要不同进度估计器时，你可以切换到 RoboMeter、recorded 曲线或自己的 PRM。 一旦后端生成进度曲线，后续后处理和指标流水线都是共享的。

使用场景 推荐后端 原因
首次运行或常规批量评估 dopamine 配合 EVAL_MODE=incremental 稳定的默认选择，提供简单的一条命令路径，并支持仅主视角、单臂和双臂视频布局。
重复或依赖上下文的动作 robometer 序列式评判相比局部成对比较可以使用更长的时间上下文。
不加载模型调试指标 recorded 使用 manifest 中的 progress 或 progress_path。
你自己的 PRM 或奖励模型 自定义适配器 返回 [0, 1] 中的绝对进度，或在计算指标前配置归一化。适配器步骤见 自定义 PRM。

Dopamine 模式

Robo-Dopamine 是成对比较式 PRM。它通过三种比较模式之一对采样状态 打分，构建进度曲线。

模式 比较对象 进度解释方式 适用场景
incremental（默认） 将上一采样状态作为 before，当前采样状态作为 after。 模型分数被视为局部进度变化，并随时间累积。 默认 v1.5 模式，用于局部逐步变化分析。如果相邻采样点过于相似，可考虑更大的 FRAME_INTERVAL。
forward 将起始帧作为 before，当前采样状态作为 after。 模型分数被视为当前绝对进度估计。 当从起点到当前状态的变化比到目标图像的距离更容易判断时使用。
backward 将目标图像作为 before，当前采样状态作为 after。 模型分数会用 progress = 1 + score 转换为进度。 适用于可提供目标图像或目标占位图，并且希望使用目标相对评分的情况。

示例：

EVAL_MODE=incremental MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh
EVAL_MODE=forward MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh
EVAL_MODE=backward MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh
成对比较式评判在重复或依赖上下文的动作中可能表现受限，因为局部成对比较可能无法揭示 策略是否正在取得进度，还是只是在来回移动。对于这些案例，可以与 RoboMeter 这类序列式后端的结果进行比较。

视角和目标图像

多视角和目标图像输入是可选的，但在操作任务中， 当进度会被单一摄像头遮挡时，它们通常可以提升评判质量。

规范视频字段

  • video：必需的主视角、第三人称或俯视视角，也是 RoboMeter 的默认视角。
  • wrist_video：单臂机器人的唯一腕部相机。Dopamine 会将它复制到后端要求的两个腕部输入槽位。
  • left_wrist_video 和 right_wrist_video：双臂机器人的左腕和右腕相机，必须成对提供。

单臂机器人使用 wrist_video，双臂机器人使用左右腕字段， 两种形式二选一，不能同时使用。 对于 Robo-Dopamine，适配器会将 video 用作主相机， 将 wrist_video 同时用于两个腕部槽位，或者将双臂机器人的左右腕字段 一一映射。如果只提供 video，适配器会将其复用于所有相机槽位， 因此快速测试也可以运行。旧版包含 high、left 和 right 的 videos 对象仍可兼容读取。

对于 RoboMeter，当前 HTTP 适配器会从 manifest 中选择一个视角进行评估。 默认使用 video。可以将 ROBOMETER_VIEW 设置为 wrist_video、left_wrist_video 或 right_wrist_video。对于单臂机器人，wrist_video 可以满足适配器要求的左腕或右腕选择。旧的 high、left 和 right 别名仍然可用。其他非默认视角缺失时，案例会报错， 而不是静默回退到其他相机。 

PRM=robometer ROBOMETER_VIEW=left_wrist_video MANIFEST=cases.jsonl bash eval/run_eval.sh

何时添加目标图像

  • 当期望的最终布局很具体时使用 goal_image，例如对象布局、颜色顺序或目标容器。
  • 对于语言指令已经足够的简单语义任务，可以省略。
  • 如果省略，而后端需要图像字段，运行器可以回退到 eval/examples/blank.png。

Multi-GPU

默认使用一个 GPU，以保持命令可预测。在更大的批次上，可以设置 GPUS 或传入 --gpus，将案例分片到本地设备。 

GPUS=0,1,2,3 MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh

每个 worker 会在分配到的 GPU 上加载一个 PRM 实例，处理自己的分片， 运行器最后合并分片输出。这是简单的本地数据并行， 通常足以处理评估批次。

也可以让运行器自动选择 GPUs。在当前实现中，GPUS=auto 会查询 nvidia-smi，选择已用显存低于 1024 MiB 的设备； 如果没有找到这样的设备，则回退到 GPU 0。 

GPUS=auto MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh

对于 RoboMeter multi-GPU runs，每个分片会使用 ROBOMETER_SERVER_PORT + shard_index 作为自动启动服务器的端口。 因此，当同一台机器上运行多个评估时，请选择空闲的基础端口。

进度标准

指标栈消费归一化绝对进度曲线。每个 PRM 适配器最终都应产生： 

progress[t] in [0, 1]
PRM 输出 计算指标前的转换方式
[0, 1] 中的绝对进度 直接使用，然后裁剪小的数值溢出。
[0, 100] 中的绝对进度 使用 --normalize 0_100 除以 100。
逐步增量进度 使用 --source-type delta，随时间累积，然后裁剪到 [0, 1]。
未校准的奖励或相似度 在指标计算前添加适配器专用校准。

不要强制曲线单调。回退和振荡是有意义的信号， 会被回撤、恢复、停滞和 regret 指标使用。 结果应同时存储 progress_raw 和 progress_processed。

后处理

默认流水线是模块化的：

  1. 将 PRM 输出归一化为 [0, 1] 中的绝对进度。
  2. 将数值裁剪到 [0, 1]。
  3. 用局部中位数替换孤立的局部异常值。默认阈值为 0.35。
  4. 使用加权时间窗口进行平滑。
p'_t = 0.1*p_{t-2} + 0.2*p_{t-1} + 0.4*p_t + 0.2*p_{t+1} + 0.1*p_{t+2}

这个默认设置旨在减少孤立尖峰和锯齿状伪影，同时不掩盖真实回退。 当人类能看到清晰上升趋势，但局部成对判断在有进度和无进度之间交替时， 它尤其有用。

当你在调试原始 PRM 行为时，可以禁用后处理：

prm-judge eval --manifest cases.jsonl --outlier-method none --smoothing none

从 CLI 修改平滑权重：

prm-judge eval --manifest cases.jsonl --smoothing-weights 0.05,0.15,0.6,0.15,0.05

权重列表应为奇数长度、非负，并且总和为正。它会被自动归一化。 如果需要更深度的自定义，请编辑 eval/prm_judge/curves.py， 尤其是 parse_smoothing_weights、weighted_smooth 和 PostprocessConfig.smoothing_weights。

指标

除非另有说明，指标会从处理后的进度曲线计算得到。 使用原始曲线进行调试，使用处理后曲线生成默认评估报告。

案例级指标

指标 解释
MaxP 达到的最大进度。对于失败但接近成功的执行案例很有用。
M25, M50, M75 里程碑指示器，表示执行过程是否跨过对应进度阈值。
SR 成功阈值下的成功指示器，默认 0.99。
PPL 以最佳达到进度为锚点的进度加权路径长度。
CRA 回退之后的 cumulative regret。应在相似成功或进度条件下比较。
Stag 近停滞状态转换的比例。应结合视频长度和数据采集方式一起解读。
MDD 最大进度回撤。
Rec 最深回撤谷底之后恢复的进度。
DRR 稳健性分数，近似为 (Rec + epsilon) / (MDD + epsilon)，并裁剪到 1。

组级 v1.5 指标

指标 适用对象 含义 默认公式
MaxP-F 失败轨迹 失败执行案例在失败前走到了多远。 对 SR_trace = 0 的轨迹取 MaxP 均值。
FNS 失败轨迹 失败执行案例的近成功质量，结合最佳达到进度和里程碑跨越情况。 0.5 * MaxP + 0.3 * M75 + 0.2 * M50；成功轨迹贡献 0。
SQS 成功轨迹 成功案例中的执行质量，奖励高效、低 regret、低停滞曲线。 0.5 * PPL + 0.3 * (1 - CRA) + 0.2 * (1 - Stag)；失败轨迹贡献 0。
RBS 全部轨迹 最大回撤之后的稳健性。 轨迹 min(1, (Rec + epsilon) / (MDD + epsilon)) 的均值。
OAS 全部轨迹 综合成功、失败案例进度、恢复和成功质量的整体审计分数。 0.3 * SQS_trace + 0.2 * FNS_trace + 0.2 * RBS_trace + 0.3 * SR_trace，再对轨迹求均值。
有些诊断是有条件的。例如，CRA 在比较达成相似进度的执行案例 时最有信息量。完全停滞的曲线可能 regret 很低，但仍然是差的执行过程。 默认情况下，成功分组使用 MaxP >= --success-threshold。 只有当基准标签应定义 success 和 failure 时，才使用 --success-source label。

自定义 PRM

工具包将两个职责分离：PRM 适配器生成进度曲线， 指标栈基于标准化曲线计算诊断结果。因此，除了 Dopamine 以外， 也可以使用其他 PRMs。

最小集成步骤

  1. 在 eval/prm_judge/prm/ 下创建新的适配器文件，并继承 BasePRMAdapter。
  2. 实现 predict(case, output_dir)，让它读取 manifest 案例、运行你的 PRM，并返回 ProgressTrace。
  3. 在 eval/prm_judge/cli.py 中注册后端名称：将其加入 --prm 选项列表，并在 build_adapter 中创建适配器。
  4. 确保返回的进度是绝对 [0, 1]，或者使用匹配的 --normalize 和 --source-type 选项运行。
  5. 使用 prm-judge eval --prm your_backend --manifest cases.jsonl 进行评估。

适配器检查清单

  • 读取 EvalCase 字段，例如视频、任务文本、目标图像和元数据。
  • 运行你的 PRM，并返回与采样帧或视频时间对齐的进度序列。
  • 判断输出是绝对进度、逐步增量，还是其他分数。
  • 判断尺度是 [0, 1]、[0, 100]，还是未校准。
  • 优先返回 [0, 1] 中的绝对进度。如果不是，请为整次运行传入匹配的 --normalize 和 --source-type 选项。
from prm_judge.prm.base import BasePRMAdapter
from prm_judge.schema import EvalCase, ProgressTrace

class MyAdapter(BasePRMAdapter):
    def predict(self, case: EvalCase, output_dir):
        scores = run_my_model(case.videos, case.task, case.goal_image)
        return ProgressTrace(
            case_id=case.case_id,
            progress=scores,
            source_scale="0_1",
            source_type="absolute",
        )

eval/prm_judge/prm/ 下的现有适配器可以作为模板。 recorded.py 是最小示例，robometer.py 展示了如何包装外部模型服务。请在你的适配器旁边记录模型的输出尺度、 语义、必需视角、目标图像行为和运行时要求。

以 RoboMeter 为例

RoboMeter 通过 HTTP 适配器集成为序列式后端。它将 outputs_progress.progress_pred 读取为 [0, 1] 中的绝对进度曲线。由于它会基于更长的序列进行推理， 因此对于局部成对评判不够充分的重复动作案例， 它是一个有用的比较对象。

当复用已有 RoboMeter 服务器时，PRM-as-a-Judge 会检查 /model_info， 并要求服务器模型路径与 PRM_PATH 匹配。这有助于避免误用旧 checkpoint 进行评估。适配器会以 .npy multipart files 上传帧数组， 从而让长视频请求更易处理。

常用命令

不移动文件，批量评估大量视频

MANIFEST=/data/my_rollouts/cases.jsonl \
PRM_PATH=/models/Robo-Dopamine-GRM-8B-Pro \
OUTPUT_ROOT=eval/results/my_rollouts \
bash eval/run_eval.sh

使用全部四个本地 GPUs

GPUS=0,1,2,3 MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh

为短操作任务运行更密集的曲线

FRAME_INTERVAL=36 MANIFEST=cases.jsonl PRM_PATH=/path/to/prm bash eval/run_eval.sh

使用 benchmark labels 进行成功分组

prm-judge eval --manifest cases.jsonl --success-source label --visualize

花费 GPU 时间前检查 manifest

prm-judge eval --manifest cases.jsonl --prm recorded --dry-run --limit 10

比较原始进度和处理后进度

prm-judge eval --manifest cases.jsonl --outlier-method none --smoothing none --visualize
prm-judge eval --manifest cases.jsonl --visualize
